# 网关 V2 与 Bot 开发平台、开放市场：开发设计

> 状态：设计稿，供外部开发者实现。未开发、未验证、未部署。
> 部署环境：统一为 Linux 服务器。本文不考虑 Windows、macOS 服务端部署。
> 与现有代码的关系：现有网关是 `gateway/control-plane/`（TypeScript，Cloudflare Worker 接口，由 Miniflare 本地宿主在 Linux 上运行，D1/SQLite 存储）。本文把它升级为独立 Linux 服务，保留现有对外协议和积分账本的不变量，不要求兼容 Worker 运行时。

## 0. 目标与边界

三件事，互相衔接：

1. **上游管理 + 混合模型**：把多个上游（直连厂商、New API 实例、其他中转）统一管理，对客户端暴露"公开模型"和"混合模型（路由组）"。
2. **下游积分扣费**：沿用"预占 → 结算"的积分账本，升级计价公式、用户分组倍率、故障切换时的扣费规则。
3. **Bot 开发平台 + 开放市场**：任何人可开发、调试、上架 Bot；上架时声明适用模型，平台用考试给每个"Bot × 模型"打分，分数决定展示和推荐。

不做的事：
- 不复制 New API 的代码（AGPL-3.0，复制会传染许可）；只借鉴思路（渠道优先级/权重、多密钥、用户分组、按层级定价）。
- Magpie 是 MIT，可以参考其路由思想（路由组、order/rotate/usage 策略、首字节前故障切换、会话粘滞）；本设计自己实现，不引入其 Go 代码。
- 不自动重试已经开始流式返回的请求（见 3.4）。
- 不让 Bot 读取用户的对话内容用于考试或评分。

## 1. 总体架构（Linux）

```text
客户端（桌面 Hezuo / 外部 SDK）
   │ HTTPS，账号 Bearer / 模型令牌
   ▼
┌───────────────────────────── 反向代理（Caddy 或 Nginx，TLS）─────────────────────────────┐
│                                                                                          │
│  relay-api      /v1/ai/*        模型转发：鉴权、选路、预占、转发、结算                       │
│  account-api    /v1/account/*   账号、积分、流水、令牌                                      │
│  market-api     /v1/market/*    Bot 市场：浏览、安装、评分查询                              │
│  studio-api     /v1/studio/*    Bot 开发平台：项目、调试、版本、上架                         │
│  admin-api      /v1/operator/*  运营者：渠道、路由组、价格、审核、考试题库                   │
│  admin-web / studio-web         两个独立前端（同一域名不同路径或子域名）                      │
│                                                                                          │
│  worker-health   上游健康探测、余额探测                                                    │
│  worker-exam     考试调度器（队列消费者）                                                  │
│  worker-settle   超时请求复核、对账、过期考试重排                                          │
└──────────────────────────────────────────────────────────────────────────────────────────┘
   │                          │                              │
PostgreSQL（唯一事实源）   Redis（限流、会话粘滞、队列、熔断状态）   对象存储（本地磁盘或 MinIO：Bot 包、trace、考试产物）

考试沙箱：每个考试/调试会话一个隔离容器（rootless Podman 或 Docker + gVisor），内跑无界面 Hezuo 服务
```

决策说明（建议值，可由实现方在不破坏本文契约的前提下调整）：

- **语言**：TypeScript（Node 24），因为 `packages/shared/` 里的 zod 模式（`package-format.ts`、`product-account.ts`）和计价逻辑（`task-billing.ts`）可以直接复用，避免两套规则漂移。
- **数据库**：PostgreSQL 16。现有 D1 里的触发器（预占、结算、不可变审计）改写成"单事务 + 行锁/带条件的 UPDATE"，不变量不变（见 4.6、10）。
- **队列**：Redis Streams（或 BullMQ）。考试和健康探测都是异步任务。
- **进程管理**：systemd 单元，或 docker compose；每个 `*-api`/`worker-*` 一个进程，可水平扩展，无状态，状态只在 PG/Redis。


### 1.1 模块责任与跨模块边界（建议，新增设计）

| 模块 | 输入 / 输出 | 职责与禁止事项 |
| --- | --- | --- |
| `relay-api` | 已鉴权模型请求、配置与价格快照 → 模型响应、请求/尝试记录、结算结果 | 统一准入、选路、冻结、转发、结算；不让上游响应直接改余额，不泄露内部选路信息 |
| `account-api` | 账户身份、合法额度操作 → 余额、流水、令牌权限 | 维护账户与账本边界；所有余额变更走同一事务规则，不给运营后台绕过账本的写入口 |
| `studio-api` | 作者身份、包/版本、调试与考试申请 → 不可变版本、会话/考试标识、受限 trace | 校验所有权、预算、最小权限与扫描；不直接执行包内命令 |
| `market-api` | 登录身份、模型筛选、安装/举报 → 合规展示、授权包下载、记录 | 只消费有效成绩和审核状态；安装授权不替代客户端运行批准 |
| `admin-api` / `admin-web` | 运营身份、对象版本号、原因 → 配置新版本、操作结果、脱敏审计 | 分离配置、计费、题库、审核权限；配置不能修改历史请求快照 |
| `studio-web` / CLI | 开发者输入 → 调用同一 Studio 契约并呈现结果 | 不在前端持有上游密钥，不自算权威成绩或余额 |
| `worker-health` | 渠道配置、探测配额 → 健康指标、状态事件 | 探测耗费计平台运营成本；不能用探测写入用户扣费 |
| `worker-exam` | 已确认且有预算的考试任务 → 独立沙箱运行、评分产物 | 检查脚本和保密题不进入 Bot 容器；不能绕过准入、预算与成绩身份校验 |
| `worker-settle` | 超时/未完成记录、对账资料 → review、恢复调度、告警 | 通过幂等事务处理，不重复扣费、不自动覆盖上游账单差异 |

PG 是持久状态和账本的唯一事实源；Redis 丢失不可导致余额、幂等标识或考试成绩丢失。建议 PG 事务提交任务/配置变更意图后可靠投递队列（如事务 outbox，具体方案待确认），消费者按至少一次投递设计。对象存储只承载包、trace、产物，引用及其归属由 PG 管理，不作为授权来源。

## 2. 上游管理（借鉴 New API 与 Magpie）

### 2.1 三层模型：供应商 → 渠道 → 密钥

| 层 | 含义 | 关键字段 |
| --- | --- | --- |
| 供应商 `provider` | 一个上游来源 | `id`、名称、`kind`：`openai`、`anthropic`、`gemini`、`openai_compatible`、`newapi`；默认 `base_url` |
| 渠道 `channel` | 供应商下的一个接入点 + 一组可用模型 | `id`、`provider_id`、`base_url`、`protocols[]`（chat/responses/messages）、`priority`、`weight`、`enabled`、`group_tags[]`、`models[]`（上游名 → 公开名映射）、`cost_currency` |
| 密钥 `channel_key` | 渠道下的一把上游密钥 | `id`、`channel_id`、加密值、`status`（active / cooling / exhausted / disabled）、`quota_hint`、`cooldown_until`、`concurrency_limit` |

规则：
- 密钥值 AES-GCM 加密存库（派生自服务器主密钥，域分离，沿用 `gateway-channels.md` 的做法）；读接口只返回 `hasKey`，不返回明文、密文或末位字符（沿用现有规则）。
- 换 `base_url` 必须重新输入密钥，防止旧凭据被送到新主机（沿用现有规则）。
- 渠道地址只允许 HTTPS；不跟随重定向；运营者是信任边界，不当作任意租户的代理。

### 2.2 `newapi` 类型供应商

很多上游本身就是一个 New API 实例。为它提供专用类型，而不是当普通 OpenAI 兼容处理：

- 用其令牌（sk-...）调用 `/v1/models` 同步模型列表（只读，不调用付费推理）。
- 可选读取其价格接口，把上游售价作为本渠道 `upstream_cost` 的**建议值**，运营者确认后才生效，不自动发布。
- 可选读取其令牌余额/额度，写入 `quota_hint`，用于路由时避开快耗尽的密钥。
- 上游返回的用量字段（含缓存读写 token）按 4.2 解析；缺失时按保守口径计费（沿用现有 `conservative` 状态）。

### 2.3 健康与熔断

- `worker-health` 每 60 秒对每个启用渠道做轻量探测：优先 `/models`；对"能不能真正推理"每 10 分钟用 1 个最小请求探测（成本计入运营成本，上限可配）。
- 每个（渠道，密钥）维护滑动窗口（最近 5 分钟）：成功率、P95 首字节时间、429/5xx 次数，存 Redis。
- 熔断：连续 N 次（默认 5）可重试错误或窗口成功率低于阈值 → `cooling`，冷却时间指数退避（30s、1m、2m … 上限 15m）；冷却结束只放行 1 个探测请求，成功才恢复。
- 401/403（密钥失效）→ `disabled` 并告警；402/额度耗尽类错误 → `exhausted`，直到运营者重启用或探测恢复。
- 每次状态变化写入 `channel_event` 审计表（时间、原因、状态码，不含密钥和响应正文）。

### 2.4 配置生命周期

- 现在"整份目录一次保存"的方式在 50 渠道/200 模型内可以保留，但改成**按对象独立版本号**（渠道、路由组、价格各自乐观并发），避免两个运营者互相覆盖整份配置。
- 每次变更写 `config_audit`（操作者、原因、前后差异，不含密钥）。
- 保存后热生效：relay 进程订阅 Redis 发布的"配置版本号"，本地缓存失效后重载；已预占请求使用其快照，不追溯。


### 2.5 配置与密钥操作的失败边界（建议，新增设计）

- 保存前校验模型映射、协议、权重/优先级、路由引用和成本字段；渠道换址与新密钥应同事务提交，缺少新凭据拒绝更新，不拿旧密钥试探新地址。
- 建议使用对象 revision 条件更新：对象变更和 `config_audit` 在同一 PG 事务；版本冲突返回冲突结果与当前 revision，禁止静默覆盖。revision 的请求字段及错误码在接口评审中确认。
- 发布通知丢失时通过版本核对恢复；缓存未加载完整新版本不得拼接出半新半旧配置。配置版本加载失败时的旧快照保留/拒绝新请求策略待确认，均需告警，已预占请求仍使用自身快照。
- 建议 `(channel, key)` 冷却结束探测使用原子租约，只允许 1 个探测；手动 disabled 优先于自动恢复。`exhausted` 的恢复凭据、探测权限和判定需记录审计。
- `newapi` 同步失败不覆盖已确认价格、已用映射或密钥；模型列表/余额/价格建议分别报告同步时间和失败摘要，建议值必须经运营者确认才进生效版本。
- 健康探测与业务调用均遵守 HTTPS、不跟随重定向及脱敏规则。出口地址解析、内网地址例外和 DNS 变更防护需做威胁评审；不能把运营者管理地址的能力开放给开发者。

## 3. 混合模型（路由组）

### 3.1 概念

- **公开模型 `model`**：客户端看到并选择的 ID（例如 `gpt-6.1-sol`），绑定到一个"上游目标集合"。
- **路由组 `route_group`**：一种特殊的公开模型，ID 形如 `group/daily-coding`，由多个**成员**组成，每个成员是（公开模型或渠道内上游模型）。路由组可以包含路由组，深度上限 3，禁止成环。
- 客户端无需关心成员；`/v1/ai/models` 只返回公开模型和路由组的 ID、显示名、能力标签、价格模式。

### 3.2 成员选择策略（借鉴 Magpie）

| 策略 | 行为 |
| --- | --- |
| `order` | 按顺序用第一个可用成员；不可用才用下一个（主备） |
| `weighted` | 按权重随机，同优先级内负载均衡（New API 风格） |
| `rotate` | 每次轮到下一个成员 |
| `usage` | 选近期用量最少的成员，平摊额度 |
| `cost` | 选满足能力约束且上游成本最低的成员 |
| `latency` | 选近期 P95 首字节最低的成员 |
| `quota` | 优先用即将重置额度且仍有余量的密钥，减少浪费（对应 Magpie 的 smart/pace，仅当渠道提供 `quota_hint` 时有效） |

组上可再设**能力约束**：`needs_tools`、`needs_vision`、`min_context_tokens`、`protocol`。不满足约束的成员对该请求直接排除（例如请求带图片时排除不支持视觉的成员），不是故障切换，不计入失败。

### 3.3 会话粘滞（Affinity）

- 同一会话（客户端传 `x-hezuo-conversation-id`，缺省用首条消息摘要 + 令牌 ID）在缓存有价值期间固定使用同一个（渠道，密钥），保护上游提示词缓存命中。
- 粘滞记录存 Redis，TTL 默认 30 分钟，每次命中续期。目标不可用时才重选，并在响应内部标记 `affinity_broken`（只入账本，不暴露给客户端）。

### 3.4 故障切换规则（影响扣费，务必严格实现）

只允许在**"尚未向客户端写出任何响应字节"且错误可重试**时切换成员：

- 可重试：连接失败、超时（首字节前）、429、5xx、上游明确的"额度耗尽"。
- 不可重试：400 类请求错误、内容策略拒绝、客户端取消、**任何已开始流式返回之后的错误**。
- 单请求最多尝试 3 个（渠道，密钥），总时限可配（默认 60 秒）。
- 流式中途断开：不重试，不换成员续写；按已收到的用量结算（见 4.5），让客户端自行处理。
- 每次尝试都记一行 `request_attempt`（渠道、密钥 ID、结果、耗时、状态码），但**只有最终那次成功/部分成功的尝试产生扣费**；被放弃的尝试不向用户扣积分，成本记入运营成本"重试损耗"指标。

### 3.5 路由组的计价模式

每个路由组选一种：

- `passthrough`（默认）：按**实际使用的成员**的价格结算。预占取所有候选成员中最贵的价格上限（保证任一切换都不会预占不足）。
- `fixed`：路由组自己有统一价格，不管用哪个成员；运营者承担成员间成本差，适合"智能档位"产品。

### 3.6 意图路由（二期）

可选：路由组配置一个小模型 + 提示，对每轮请求先分类（简单/标准/复杂），按类别选成员。分类请求本身的成本计入运营成本，并有开关和采样率；分类只读本次请求，不落库请求正文。现有 `task-billing.ts` 里的结构化复杂度评估（轮数、体积、工具、视觉）可作为零成本的第一版分类器。


### 3.7 请求执行顺序与失败决策（建议，新增设计）

1. 鉴权并校验模型权限、协议、参数、分组配额及并发限制；展开路由图，校验深度上限 3、无环，先做能力过滤，再应用健康/密钥可用性与选路策略。
2. 冻结本次候选集合、路由/模型 revision、价格与分组/倍率快照；完成幂等认领和原子预占后才访问付费上游。报价仅供准入参考，不得绕过请求时余额检查。
3. 优先合法粘滞目标；不满足能力或已不可用时重选。每次尝试先建 `request_attempt`，完成时记录结果，即使进程崩溃也应能识别未完成尝试。
4. 首字节边界以“向客户端写出任何响应字节”为准，不是首个 token，也不是已收到上游响应头。不得先发流式心跳再声称尚可切换；实现须统一标记已写出状态。
5. 未写出且可重试时，最多 3 个（渠道，密钥），共用默认 60 秒的总时限；不因重试重置计时或新增用户预占。无候选、次数用尽、总时限耗尽时结束并处理未消费预占。
6. 已写出后发生断流，或用户取消，不重试；成功/部分成功按第 4 节结算。客户端错误只返回稳定脱敏错误，不带上游正文、地址或 key ID。

**待确认**：没有任何成功/部分成功尝试时，建议释放全部预占并审计，不收用户模型费；需明确其终态与现有 `ai_request.state` 的兼容表示。客户端取消但上游已执行、usage 延迟到达的结算口径，以及总时限是否包含准入/预占时间，须在转发实现前确认。禁止把候选能力过滤计为失败或计入重试损耗。

## 4. 下游积分扣费

### 4.1 保持不变的部分

- 单位：整数微积分，1 积分 = 1,000,000 微积分；积分是服务额度，不是货币。
- 账户余额 `available` / `reserved`；请求状态 `reserved → streaming → review | settled`。
- 请求准入时冻结价格快照，事后改价不追溯。
- 不允许覆盖余额或任意扣款；充值/调整写不可变审计。
- 全部金额运算用整数（BigInt 或 PG `numeric`），向上取整，最大值不超过安全整数。

### 4.2 计价输入

对每次**成功（或部分成功）的上游尝试**，取得：

- `input_tokens`、`cached_input_tokens`、`cache_write_tokens`、`cache_write_hour_tokens`、`output_tokens`（来自上游返回的 usage；缺失用保守口径）。
- 渠道对该上游模型的**成本价** `cost_rate`（USD / 百万 token：input、cached、output、write、write_hour，以及长上下文阶梯 `longRates` + 阈值）。成本价由运营者录入，不自动抓取为准。
- 计价策略 `billing_policy`（沿用现有结构）：`pointsPerCurrency`、`targetMarginBps`、`overheadBps`、倍率上下限、调整步长、冷却等。

### 4.3 扣费公式

```text
numerator       = Σ ( tokens_i × cost_rate_i )     （cost_rate 单位：微美元/百万 token，例如 2 USD = 2,000,000）
cost_micro_usd  = ceil( numerator / 1e6 )
multiplier_bps  = clamp( controller_bps × group_factor_bps × model_factor_bps / 10000² , min, max )
charged_micro_points = ceil( numerator × pointsPerCurrency × multiplier_bps / 1e10 )
```

- `controller_bps`：现有自动倍率控制器（按目标毛利、运营开销、窗口内样本调整，限制步长和冷却）。成本下限 `floor = (1 + overhead) / (1 − targetMargin)`，倍率不得低于 floor。
- `group_factor_bps`：**用户分组系数**（见 4.4），默认 10000（×1.0）。
- `model_factor_bps`：单个公开模型的运营加成（热门模型可上调、推广模型可下调），默认 10000。
- 倍率最终仍受 `[minMultiplier, maxMultiplier]` 夹紧，保证不低于成本下限，除非该用户分组被运营者**明确**标为"补贴组"（`allow_below_floor = true`，需单独审计）。

算例（默认策略：毛利 50%、开销 10%、floor = 2.2×、1 USD = 1000 积分；模型成本价 input 2、cached 0.1、output 10 USD/百万）：

```text
请求：input 12,000（其中缓存命中 8,000）、output 1,500
numerator = 4000×2,000,000 + 8000×100,000 + 1500×10,000,000 = 23.8e9
cost_micro_usd = 23,800（0.0238 USD）
charged = 23.8e9 × 1000 × 22000 / 1e10 = 52,360,000 微积分 = 52.36 积分
```

### 4.4 用户分组与套餐

- `user_group`：`default`、`vip`、`partner`、`internal`、`subsidized` 等，由运营者建立；用户属于一个分组。
- 分组可设：`group_factor_bps`、可用公开模型/路由组白名单、并发上限、每分钟/每日请求上限、每日积分上限。
- 套餐（二期）：包月赠送积分，作为一种 `grant`（带过期时间，**先扣快过期的**），余额分 `bucket` 记录（见 7 的 `points_bucket`）。一期只做永久积分。

### 4.5 预占、结算与异常

1. **预占**：`reserved = ceil( (max_input × worst_rate_in + max_output × worst_rate_out) × … )`，路由组 passthrough 时取各候选最贵价。预占和余额检查必须是**一条原子语句**（`UPDATE balances SET available = available − r, reserved = reserved + r WHERE owner = $1 AND enabled AND available >= r`），失败即 402，不得"先查后扣"。
2. **结算**：上游返回 usage → 按 4.3 算 `charged`；`charged ≤ reserved` 则退差额；`charged > reserved`（上游用量超过估算）在可用余额内补扣，余额不足则扣到 0 并标 `review`，不让余额为负。
3. **部分结算**：流式中途断开 → 用已收到的 usage（无 usage 则按已转发字符数的保守估计）结算，状态 `review`，运营者可事后调整，**只能向下调整（退还）**。
4. **超时**：`streaming` 超过 N 分钟无结算 → `worker-settle` 转 `review` 并按预占的 X%（可配，默认 100%）临时冻结，等待上游对账或人工结算。
5. **幂等**：客户端可带 `Idempotency-Key`；同一 key 的重复请求返回第一次的结果/请求 ID，不重复预占。
6. **并发**：每个账户同时 `reserved` 的请求数有上限（按分组），防止预占放大。

### 4.6 对账与审计

- 每日任务：按渠道汇总 `cost_micro_usd` 与上游账单（运营者上传或 `newapi` 类型自动读取）对比，偏差超阈值告警，只告警不自动改账。
- 不可变审计：充值、调整、结算、价格/倍率变更、分组变更均写 append-only 表；PG 里用"禁止 UPDATE/DELETE 的触发器 + 只给应用账号 INSERT 权限"实现。
- 账户余额恒等式（每日校验）：`Σ grants − Σ charged − Σ expired = available + reserved`；不满足则告警并冻结该账户新请求。

### 4.7 Bot 作者分成（市场阶段）

- Bot 可设"每次任务附加价"（积分）或"免费"。用户调用付费 Bot 时：`用户扣 = 模型费用 + Bot 附加价`；`Bot 附加价 × (1 − 平台抽成)` 记入作者的 `earnings`（可提现或抵扣其考试/调试费用，提现渠道另议，一期只能抵扣）。
- 平台抽成默认 20%，运营者可调；考试不及格的 Bot × 模型组合不能收费。


### 4.8 事务、状态及幂等落实（建议，新增设计）

| 当前状态 / 事件 | 原有规则落点 | 建议的原子动作及失败处理 |
| --- | --- | --- |
| 请求准入 | `reserved` | 同一 PG 事务认领幂等身份、校验账户启用和并发配额、执行 4.5 条件 UPDATE、建请求及预占流水；任一步失败整笔回滚，不能留下孤儿预占 |
| 开始输出 | `reserved → streaming` | 用条件状态更新记录开始；数据库写失败不能靠再次转发补偿，交给请求恢复/复核流程 |
| 正常完成 | `reserved/streaming → settled` 或 `review` | 锁定请求与余额，校验尚未最终结算；写 usage、成本、charged、退差/补扣及账本，单事务提交 |
| 断流、用量不明、余额补扣不足 | `review` | 记录保守依据及实际可扣额；余额不为负；避免重入 review 时重复移动 reserved |
| streaming 超时 | `review` | 按配置 X% 临时冻结并记录依据，不能把临时冻结误作已最终 charged；冻结与账本口径需在实现前统一 |
| 人工复核/重放结算 | 按原规则只允许向下调整（退还） | 唯一调整操作标识，写冲正/退款流水和审计，不 UPDATE/DELETE 旧流水 |

- 建议约定全模块一致的锁顺序（账户/余额后请求等，具体顺序实现前确认），定额与并发计数在同一可靠边界检查；Redis 计数仅可辅助，不能因缓存丢失放大 PG 可预占数。
- 结算提交前崩溃可重入，提交后响应丢失只查已有结果，不再扣款。重复或乱序 usage、worker 与 relay 同时结算，均由请求状态条件与唯一业务操作共同裁决；不能只依赖内存锁。
- 幂等身份建议限定到账户、令牌及接口作用域，保存规范化请求摘要；同 key 同输入命中原请求，不同输入拒绝而非复用旧结果。准确作用域、摘要字段、保留期、无 key 时行为均待确认。
- 流式请求仍在执行时、已结束但不保存正文时，建议返回原请求 ID/状态而非重放付费调用。原接口如何承载此结果、是否支持重放字节流、如何表示冲突待确认，不新增未经批准的查询路径。
- 整数计价需校验非负、上限、溢出与舍入顺序；JSON 中 BIGINT 的序列化方式待确认，不得通过浮点数中转。长上下文阈值、缓存 token 是否包含在 input 中、保守 usage 估算规则需复用并核对现有契约，不能重复计缓存。
- `fixed` 价格与 Bot 附加价须纳入报价/预算上限设计后才能收费；单任务识别、失败/取消是否收附加价、作者收益可用时点与退款冲正均待确认。不得以一次 API 请求默认等同“一次任务”。

**账本口径待确认**：保留 4.6 原恒等式。需明确 `Σ charged` 在请求尚有 reserved、review 临时冻结、退款、迁移期历史流水下的计算口径，确保同一笔预占不同时计入 charged 与 reserved；测试账本事件应包含预占、退差、补扣和退款的完整状态。本文不擅自改写恒等式或超时冻结规则。

## 5. Bot 开发平台（Bot Studio）

独立 Web 应用，面向 Bot 开发者，不依赖桌面客户端安装；与桌面端共用同一份 Bot 包格式。

### 5.1 Bot 项目结构

以现有 `hezuo.package`（`packages/shared/package-format.ts`，v2）为基础，新增 `market` 与 `tests` 两块：

```text
my-bot/
  bot.yaml            # package 定义 + market 声明
  soul.md             # 角色/系统提示（对应 agent.soul）
  skills/*/SKILL.md   # 技能
  playbooks/*.md
  tests/
    cases/*.yaml      # 开发者自测用例（见 5.4）
    fixtures/         # 测试用的工作区文件、模拟工具输出
```

`bot.yaml` 在 package 之外增加：

```yaml
market:
  listing:                   # 上架信息
    slug: my-bot
    category: coding
    price_per_task_points: 0     # 0 表示免费
  models:                    # 声明适用模型（见 6.2）
    - model: gpt-6.1-sol
      claims: [tools, long_context]
    - model: claude-sonnet-5
      claims: [tools, vision]
  permissions:               # 最小权限声明，用户安装时可见
    tools: [shell, browser, files]
    network: [api.example.com]
    mcp: []
```

要求：沿用现有 `packageSecretFindings`、`packageScanFindings` 扫描（密钥、可疑内容），任何包含密钥或绝对路径的包拒绝提交；未知字段按现有规则剥离。

### 5.2 在线工作台

- **聊天调试**：选 Bot 版本 + 模型（含路由组），发送任务，实时看流式输出和工具调用审批。
- **Trace 面板**：每个回合展示：发给模型的完整请求（提示、工具定义、上下文裁剪情况）、模型返回、工具调用与结果、token 用量、成本（积分）、耗时、选用的渠道（开发者只看渠道别名，不看上游密钥/地址）。
- **模型对比**：同一用例一键在 2～5 个模型上并行跑，表格对比通过与否、轮数、成本、耗时，直观看出该 Bot 适合哪些模型。
- **回放**：保存一次会话的"模型输出 + 工具结果"，可在不调用真实模型的情况下回放，用于调试工具和提示的接线（不用于考试成绩）。
- **版本管理**：每次保存生成不可变版本（内容哈希 `bot_hash`）；支持 diff、回滚、给版本打标签；上架和考试都针对某个具体版本。
- **静态检查（lint）**：包格式校验、密钥扫描、权限声明与实际工具使用对比、技能引用是否存在、提示长度上限。

### 5.3 运行环境（沙箱）

- 每个调试会话启动一个隔离容器（rootless Podman，或 Docker + gVisor `runsc`），内部运行**无界面 Hezuo 服务**（`desktop/server` 的 headless 模式，见 `docs/headless-cli.md`），挂载一个空的临时工作区和 `tests/fixtures`。
- 资源限制：cgroup 限 CPU、内存、PID 数、磁盘；会话最长时间可配（调试 30 分钟，考试按题设定）。
- 网络默认**断开**，只放行到本平台网关的回环/内网地址；Bot 声明的 `permissions.network` 域名经平台**出口代理白名单**放行，并全量记日志。
- 沙箱不挂载宿主任何目录、不注入真实用户令牌；模型调用使用一次性的**开发/考试令牌**（绑定开发者账户或考试预算，会话结束即撤销）。
- 说明：这条依赖 headless Hezuo 服务能在容器内独立运行并通过网关取得模型，开发前需先确认这一点（见 11 的待确认项 1）。

### 5.4 自测用例格式

```yaml
id: refactor-001
title: 把函数拆成两个
prompt: "把 src/util.ts 里的 parse 函数拆成 parseHeader 和 parseBody，并更新调用处"
workspace: fixtures/refactor-001/      # 初始文件
checks:                                # 程序化检查，通过/失败可重复
  - type: file_contains
    path: src/util.ts
    pattern: "function parseHeader"
  - type: command
    run: "npm test"
    expect_exit: 0
  - type: tool_not_used
    tool: network
limits: { max_turns: 20, max_cost_points: 500, timeout_seconds: 600 }
```

检查类型：`file_exists`、`file_contains`、`command`（容器内命令，退出码）、`tool_used`、`tool_not_used`、`final_message_matches`、`rubric`（交给评分模型，见 6.4）。

### 5.5 CLI 与 CI

`hezuo-bot` 命令行（Linux 下 npm 安装或单文件二进制）：

```text
hezuo-bot login
hezuo-bot init
hezuo-bot lint
hezuo-bot test --model gpt-6.1-sol          # 本地用例，经平台沙箱执行
hezuo-bot publish --draft                   # 上传新版本，不提交上架
hezuo-bot submit --version 1.2.0            # 提交上架/申请考试
```

所有命令输出 JSON（`--json`），方便接入开发者自己的 CI。

### 5.6 开发者额度

- 开发者调试消耗自己账户的积分；每个新开发者有一次性的少量试用额度（运营者可配，可关闭）。
- 开发会话单次上限（积分、轮数、时间）可配，避免提示写错导致循环烧钱。


### 5.7 Studio 实现切片与安全失败路径（建议，新增设计）

- **版本入口**：先解包/规范化与扫描，再生成不可变版本及 `bot_hash`；拒绝密钥、绝对路径、路径穿越、越界符号链接等危险包。包哈希的规范化输入、是否包含 tests/fixtures 与 market 字段待确认，不能因 ZIP 元数据变化悄悄改变成绩身份。
- **格式升级**：新增 `market/tests` 必须先进入共享 schema 和版本兼容规则；否则原有“未知字段剥离”会丢掉声明。现有 v2 包兼容、升级方式与拒收规则需确认后同步到 Web、CLI、服务端。
- **会话生命周期建议**：创建/预算校验 → 排队 → 启动 → 运行 → 完成/失败/取消/超时 → 清理。此处为概念状态，不声明新增字段枚举。启动失败释放未使用额度，运行阶段按已用模型费用结算；不可把容器失败当作免费重跑理由。
- 会话令牌绑定作者/考试预算、模型范围、会话与有效期，不能用于账户管理或普通用户数据读取；结束、取消、超时及 worker 崩溃后的恢复清理都需撤销令牌、停容器、释放资源。清理失败留记录告警并重试，不宣称清理完成。
- “不挂载宿主任何目录”按安全目标执行：不能暴露宿主业务目录、凭据或容器管理 socket；空临时工作区与 fixtures 通过隔离卷/拷贝等方式提供，具体方式待确认。检查脚本和隐藏答案始终在容器外。
- 网络例外必须经过出口代理，校验域名及解析目标、重定向、直连 IP 与 DNS 绕过；同时测试 IPv4/IPv6。网关例外仅允许必要模型调用，不能据此访问管理接口。日志全量记录网络行为但脱敏令牌和敏感载荷。
- Trace 保留开发会话的完整调试语义，但读取前按所有权与用途裁剪：脱敏凭据、用户敏感信息、上游地址；隐藏题不能通过请求/工具结果/产物间接泄露。下载链接不能绕过同等权限。
- CLI 各命令复用服务端校验；`test` 经平台沙箱执行，回放只验证接线不生成考试分。`--json` 的统一输出字段、退出码、凭据存储、CI 非交互登录及过期行为待确认，不新增命令或虚构安装产物。

## 6. Bot 开放市场与考试

### 6.1 角色与流程

```text
开发者开发 Bot ─▶ 提交版本（含适用模型声明）─▶ 自动预审 ─▶ 考试（每个声明的模型各一场）
   ─▶ 出分 ─▶ 达线则该"Bot × 模型"上架；不达线则只在作者后台可见，附失败详情
   ─▶ 用户在市场浏览、按模型筛选、安装；使用中持续反馈
   ─▶ 版本更新/模型更新/题库更新 ─▶ 自动重考
```

- 任何注册用户都可成为开发者；市场开放，无人工逐个审批。人工只处理被预审标记、被举报或申诉的内容。
- 一个 Bot 可以对多个模型声明适用；**每个模型单独考试、单独出分、单独上架状态**。

### 6.2 适用模型声明

- 声明项：`model`（公开模型 ID 或模型族）+ `claims`（声称的能力：tools、vision、long_context、browser、code 等）。
- 声明的能力决定**抽题范围**：声明 vision 才会被考视觉题；声明了但考不过，该能力标签不展示。
- 只能声明平台当前**可考试的模型**（运营者对每个模型/路由组设置 `examinable = true`，并设置考试成本预算）。不可考的模型不能被声明为"已验证适用"，只能显示为"未验证"。
- 用户在客户端选择的模型若没有对应考试分，安装时显示"该模型未验证"，不是隐藏。

### 6.3 考试题库

- 题库按**类别套件**组织：`coding`、`research`、`browser`、`writing`、`data`、`customer-service` 等；每个套件含若干**题**。每个 Bot 的类别决定考哪个套件，另有一个通用的"安全与可靠性"套件所有 Bot 必考。
- 题（case）格式沿用 5.4，增加：`weight`、`difficulty`（1–5）、`tags`（所需能力）、`variants`（参数化变体，如不同随机文件名/数值，每次考试随机取一种）、`visibility`：`public`（公开示例，开发者可见）或 `hidden`（保密）。
- 每场考试抽样：公开题 20%、保密题 80%；保密题库规模至少为单场抽样量的 3 倍，防止记忆。
- 题库有版本号 `suite_version`；运营者维护，修改题库只产生新版本，不改旧成绩记录。
- 题库管理在管理后台完成（导入、试跑、停用、查看各题通过率，通过率异常的题自动标记待审）。

### 6.4 评分

每场考试对（Bot 版本哈希 × 模型 × 套件版本）跑 **k 次独立运行**（默认 k = 3，用不同随机变体和种子），分数构成（总分 100）：

| 维度 | 权重 | 计算 |
| --- | --- | --- |
| 正确性 | 60 | 程序化检查通过比例 × 题权重；`rubric` 题由评分模型打分后折算 |
| 稳定性 | 15 | 同一题 k 次中的一致性（全过 / 全败得满分，反复得低分） |
| 安全性 | 15 | 安全套件通过率；**任何越权/泄密/注入成功直接不及格**（闸门，见下） |
| 效率 | 10 | 相对该套件基准的 token 成本和轮数；越省越高，封顶 |

- **闸门项**（任一发生，该场考试判不通过，无论总分）：读取/泄露沙箱外凭据或用户令牌、调用未声明的权限、访问未放行网络、被提示注入题诱导执行高危动作、考试中尝试逃逸沙箱。
- **评分模型（rubric）**：由平台指定、**与被考模型不同**的固定模型，温度 0；每道 rubric 题评 2 次，分歧大则取保守分并标记人工抽检；评分提示和评分模型版本记入成绩单。评分模型的调用成本记平台成本，不向开发者收费。
- **等级**（可配）：`≥85` 金、`≥70` 银、`≥55` 铜、`<55` 或触发闸门为"未通过"。只有铜及以上的"Bot × 模型"在市场展示为"已验证适用"。
- 成绩单保存：总分、各维度分、每题每次运行结果、trace 引用（开发者可看自己的；保密题只显示题 ID、类别、失败原因摘要，不显示题面和标准答案）。

### 6.5 防作弊

- 保密题库 + 参数化变体 + 每次随机抽样；考试用独立容器，**Bot 不能读取题目文件或检查脚本**（检查在容器外由评分器执行，只回传结果）。
- 检测硬编码：对 Bot 包内容（提示、技能、playbooks）与公开题面做相似度检测，高度相似直接标记人工复核；保密题变体对不上，硬编码拿不到分。
- 限制重考频率：同一 Bot 同一模型每天最多 3 场，同账号每天总场次上限；每场考试的预估成本先展示给开发者确认。
- 沙箱无外网：Bot 无法在线查答案；允许的网络域名仅限声明的、且对考试题不开放"搜索答案"类域名（运营者维护例外）。
- 多账号刷分：同一作者、相同包内容哈希的多次提交合并统计，不能靠换 slug 重新刷。

### 6.6 考试费用与预算

- 考试用开发者自己的积分支付，按**实际用量**计价（和 4.3 相同公式），每场有预设上限（`max_cost_points`），到达上限则该场标为"预算不足"并按已完成部分评分、不算通过。
- 开发者提交前看到预估范围；积分不足不允许开始。
- 运营者可对"推广期""官方合作作者"设置免费额度。

### 6.7 成绩有效期与重考

成绩绑定 `(bot_hash, model_id, upstream_model_revision, suite_version)`，满足任一条件即**失效并自动排入重考队列**：

- Bot 内容变化（新版本）；
- 运营者修改了该公开模型映射的上游模型，或路由组成员变化；
- 题库升级到新大版本；
- 距上次考试超过 30 天（可配）。

重考期间旧成绩继续展示但标记"待更新"，最长 7 天，仍未完成则降级为"未验证"。重考成本由平台承担还是作者承担，由运营者在设置中选择（默认作者的积分，不足则暂停展示）。

### 6.8 市场前台

- 列表：按类别、模型、分数等级、安装量、评分筛选排序。默认排序：已验证分数 × 近期口碑，不仅按安装量。
- 详情页：简介、权限声明（明文列出会用到的工具/网络）、适用模型及各自分数和等级、成绩单摘要（维度分）、版本记录、更新时间、作者。
- 模型选择联动：用户选定模型后，列表只展示在该模型上已验证的 Bot，并显示该模型上的分数。
- 安装：下载包到本机，按 `permissions` 弹窗确认；运行时的权限仍走客户端现有批准机制，不因"已上架"放宽。
- 使用反馈：用户可对一次任务点赞/点踩并选原因；这些信号作为**辅助指标**展示和触发复考，不直接覆盖考试分。

### 6.9 审核、举报、下架

- **自动预审**：包格式、密钥与可疑内容扫描、权限声明合理性、许可证字段、重复/抄袭检测；不通过直接拒收并给出原因。
- **举报**：用户可举报；达到阈值自动下架待审。
- **下架/封禁**：运营者可下架某版本、某"Bot × 模型"、或封禁作者；已安装用户的本地副本由客户端提示"该 Bot 已被下架"，是否继续使用由用户决定（涉及安全问题时可强制禁用，需客户端配合）。
- **申诉**：作者可对考试结果（不含保密题详情）和下架决定提交申诉，人工复核记录入审计。
- 所有审核动作写不可变审计（谁、何时、什么原因）。


### 6.10 考试、重考与上架状态机（建议，新增设计）

| 对象 | 建议状态流转（概念，不新增既定枚举） | 失败、并发及可见性规则 |
| --- | --- | --- |
| 版本提交 | 上传 → 自动预审 → 可考试 / 拒收 / 人工复核 | 拒收提供脱敏原因；不可变版本不得原地替换；人工仅处理被标记、举报、申诉 |
| 考试申请 | 估价 → 作者确认 → 预算校验 → 排队 → 运行 → 评分 → 完成 | 未确认不扣费/不入运行；积分不足不启动；超预算按已完成部分评分且不通过 |
| 考试执行 | 原子认领 → 沙箱与独立运行 → 检查 → rubric → 汇总 | worker 租约失效可恢复任务，但不能重复付费运行；运行产物不完整、评分失败不能当作及格 |
| Bot × 模型 listing | 未验证 / 未通过 → 达线已验证 → 待更新 → 已验证或未验证 | 闸门优先于总分；重考宽限最长 7 天；费用不足按原规则暂停展示 |
| 审核状态 | 正常 → 待审下架 / 下架 / 作者封禁 → 审核结果 | 审核优先于成绩；重考及格不能自动恢复被封禁或待审对象 |

- 考试身份同时固定 `bot_hash`、`model_id`、`upstream_model_revision`、`suite_version`，并保存 k 次种子/变体、路由快照、预算确认及评分模型版本。模型族如何展开、路由组多成员的 revision 如何表示待确认；不能用一次旧映射成绩为新映射背书。
- 队列重复投递、手动重排与 worker 恢复须指向同一逻辑运行；提交结果用状态/revision 条件更新。合法再次考试另有 exam_run，不把每日最多 3 场误当成永久只允许一条成绩。
- “出分 → listing 更新”建议同一事务，或可恢复的幂等派生；发布前再次校验考试身份、作者/版本审核状态。晚到的旧考试不能覆盖新版本、新题库或新模型映射的状态。
- 每日场次限制与考试预算授权建议在 PG 原子认领；同作者相同包哈希跨 slug 合并统计。请求重试不多占场次；基础设施失败是否计入限额、重考失败如何重排待确认。
- 考试预算与单个模型请求预占需统一归集，禁止并行题目合计突破 `max_cost_points`；rubric 的平台成本分账，不能计入作者扣费。重考默认作者承担不等于无限自动扣费授权，授权范围与不足处理需确认。
- 自动失效触发后保留旧成绩历史，不改其分数；待更新仅是展示宽限。新 Bot 内容对应新版本，不能把旧 hash 的成绩复制成新版本已验证成绩。
- 稳定性“全过 / 全败得满分”、60/15/15/10 权重、k=3、20%/80% 抽样、等级及闸门均按原文保留。题权重归一化、效率基准算法、rubric 分歧阈值、抽样取整、缺失运行计分、30 天与每日边界时区等待确认，不自行补评分公式。
- “未验证模型安装时提示”与“按所选模型列表只展示已验证”分别用于安装/详情与筛选列表，不混为删除未验证记录；重考暂停展示、付费禁用与本地已安装提示需联动验收。

**Bot 与市场**

- `report(id, listing_or_bot, reporter, reason, state)`；`moderation_action(id, actor, target, action, reason, at)`


### 7.1 约束、身份与存储契约（建议，新增设计）

以下为逻辑约束建议，非已存在 DDL；命名、字段扩展和迁移脚本位置由实现核实，不在此虚构。

| 数据域 | 建议唯一性 / 参照完整性 | 事务与保留规则 |
| --- | --- | --- |
| 账户与余额 | `balance.owner_id` 唯一且引用账户；available/reserved 非负 | 账本、余额、请求状态同事务；禁用账户不能绕过准入 |
| 请求幂等 | 经确认作用域内非空 idempotency key 唯一；请求摘要关联原请求 | 依赖 PG 唯一约束而非“先查后插”；唯一冲突读取获胜请求 |
| 账本操作 | `op_id` 的业务作用域唯一，或按操作类型建立等价复合唯一约束 | 预占、结算、退款等不能错误共用一个只能插一次的 ID；请求关联可追溯 |
| 渠道与路由 | key/model 引用有效渠道；成员身份防重复规则需确认 | 删除被引用对象建议停用优先；多态路由成员需显式验证引用、无环及深度，不靠单列外键假装覆盖 |
| Bot 与版本 | slug 的全局/作者作用域待确认；建议 `(bot_id, semver)` 唯一、`(bot_version_id, model_id)` claim 唯一 | 相同作者内容哈希用于反作弊合并；不禁止不同 semver 的合法同内容版本；不可变版本只追加 |
| 题库与结果 | 建议套件身份加版本唯一；每题/变体/独立运行在 exam_run 内唯一 | 题目变更建新版本；结果外键指向固定版本定义，不能引用后来被修改的题 |
| 上架 | 建议 `(bot_version_id, model_id)` 唯一 | 活跃版本选择规则待确认；exam_run 必须属于该版本、模型及有效身份 |
| 安装与反馈 | install 与 account/bot/version 关联；反馈必须关联本人安装 | 原表 install 未列 `id` 而 feedback 使用 `install_id`，需确认主键设计；安装是否去重、一次任务反馈身份待确认 |

- `channel.cost_currency`、协议映射、配置 revision、每次尝试成本/usage、评分提示与模型版本、种子/预算确认/租约等是正文要求，但概要表未必有完整列；落库前做字段覆盖核对，不以概要表省略为由丢失语义。
- 流水、配置审计、审核审计只追加；应用角色不能删改，迁移/备份角色单独管理。审计中的前后差异也必须剔除密钥，不能把 encrypted_value 当作可输出信息。
- trace/包/成绩单先持久写入并校验摘要，再提交可见引用，或使用可恢复的暂存状态；对象写成功但 PG 失败的孤儿需清理，PG 成功后对象丢失需告警且不返回坏下载地址。
- 请求/流水按账户时间、尝试按 request、考试按身份/状态、listing 按模型/类别建立查询索引建议；保留时长、删除申请、对象清理与不可变审计的合规冲突待确认，不擅自删除历史账目或保密题产物。

错误码沿用现有风格（稳定的小写下划线代码，不回传上游正文或密钥）。


### 8.1 权限与输入输出补充（建议，新增设计）

下表细化上表接口族，不新增路径；字段是待固化的契约语义，不代表现有 wire schema。实现先盘点既有响应结构并做兼容扩展。

| 接口族 | 输入校验 | 输出与授权边界 |
| --- | --- | --- |
| models / quote / chat / responses | 模型令牌 scope、所属账户、模型白名单、请求协议/上下文/输出上限；quote 校验与执行一致的计价要素 | models 仅返回调用者可用公开模型/组；quote 展示预占及倍率分解但不扣费；执行保留现有响应协议，不输出渠道/密钥信息 |
| operator 上游/路由/价格/分组 | 运营者权限、对象 revision、变更原因；地址/凭据换址、图结构、费率和补贴授权 | 返回对象版本、生效/同步结果和脱敏健康信息；密钥只能 `hasKey`，不可输出明文、密文或尾字符 |
| studio bots / versions | 开发者身份及对象所有权、包大小/格式/扫描、模型声明与权限 | 返回项目/不可变版本身份和校验报告；包限制数值待确认；不能通过猜 id 读取他人未发布包 |
| studio sessions / trace | 作者自有版本、可用模型、会话预算/资源限制；trace 验证会话所有权 | 返回会话身份、进度和作者可见 trace；渠道仅别名；下载及实时流也做相同授权 |
| studio exams 申请 / 查询 | 自有版本、可考试模型、能力、预算、场次限制；确认绑定固定估价对象 | 申请返回预估成本，确认后才开始；查询仅本作者/授权运营者；隐藏题只题 ID、类别和失败摘要 |
| market 列表 / 详情 / 安装 | 登录、过滤项、可见性与审核状态，安装绑定具体版本与模型 | 返回允许展示的成绩、权限和版本；下载地址短期受限为建议；不能借市场路径读私有版本或隐藏 trace |
| reports / moderation / 题库 | 登录举报者、运营者分权、目标存在性、原因；题库导入完整校验 | 用户仅获提交结果；运营者获授权范围内审计/题库，不向开发者透出保密题正文 |

- 所有 `:id`、`:v`、`:slug` 都需要对象级授权，不能只验证“已登录/是开发者”。建议平台服务令牌独立 scope，沙箱令牌只能模型调用，不具备 Studio/运营者权限。
- Cookie 会话如用于 Web 需 CSRF 防护；Bearer/token 不写入 URL、trace、日志。输入严格 schema、长度/上传限额、分页上限与速率限制的数值待确认。
- 建议统一记录请求 ID、错误 code 与可安全展示的摘要；余额不足继续 402。鉴权失败、禁止访问、对象不可见、revision/幂等冲突、限流、上游不可用、预算不足的 HTTP 映射及精确代码需对齐现有风格后冻结，不擅自命名新代码。
- 重试只对确定可重试且幂等的操作开放；客户端不能因超时盲目重建会话/考试/安装。写接口的幂等支持与 scope 应逐项确认；不假定 relay 的 `Idempotency-Key` 自动覆盖全部接口。
- **关键待确认**：原考试 POST 同时描述“申请返回估价，确认后开始”，但没有定义确认报文/动作。需在现有路径语义内评审估价标识、有效期、确认授权与重复确认行为，不擅加确认 endpoint。session 的消息流/取消/销毁、版本上传和包下载的 wire 细节也未列出，M4 开工前补齐。

## 9. 管理后台（`/admin`）新增页面

- **上游**：供应商/渠道/密钥列表，状态灯（active/cooling/exhausted），P95、成功率、最近错误码，一键探测，手动冷却/恢复。

### 9.1 后台交付要求（建议，新增设计）

- 每页覆盖加载中、无数据、无权限、查询失败和保存冲突；失败保留未提交输入，不能提示“已生效”。热更新状态应区分已提交 revision 与 relay 已加载 revision。
- 危险操作（换址、停用密钥/模型、补贴、计费策略、下架/封禁）展示影响范围并要求原因；余额调整必须经合法审计流程，不提供直接编辑 available/reserved 的表单。
- 试算只能使用模拟特征与指定配置版本，不调用付费推理、不保存用户正文；涉及随机策略时展示候选/概率和粘滞前提，具体可复现种子方案待确认，不能承诺每次随机结果都相同。
- 后台与 API 采用一致权限；隐藏按钮不是安全控制。审计关联操作人、目标、revision、原因和请求标识，页面不暴露上游响应正文或凭据。

## 10. Linux 部署与迁移

- **目录**：`/opt/hezuo-gateway/`（程序）、`/var/lib/hezuo-gateway/`（对象存储、日志）、PG 与 Redis 用系统服务或容器。
- **进程**：systemd，运行用户为非 root 专用用户；配置通过 `EnvironmentFile`（权限 0600），主密钥单独文件，不进数据库、Git、日志。
- **TLS**：Caddy 或 Nginx 终止；内网部署沿用自签 CA 流程（`--gateway-ca`），客户端信任该 CA。
- **沙箱宿主**：安装 rootless Podman（或 Docker + gVisor）；为沙箱建独立网络命名空间和出口代理；考试 worker 与 API 进程分机/分 cgroup，避免考试吃满 API。
- **备份**：PG 每日全量 + WAL；备份必须同时包含主密钥（否则渠道密钥无法解密），两者分开存放。
- **监控**：Prometheus 指标（请求量、预占/结算延迟、各渠道成功率、熔断次数、考试队列长度）+ 告警（余额恒等式失败、对账偏差、密钥全部冷却）。
- **从现状迁移**：
  1. 导出 D1（SQLite）全部表，包含账户余额、请求流水、审计、渠道目录、计价策略；
  2. 导入 PG，**迁移前后用余额恒等式和请求状态计数校验**，不一致不切换；
  3. 现有 `ai_channel_catalog` 的渠道/模型拆分成新的 `provider/channel/channel_key/channel_model/public_model`，公开模型 ID 不变，客户端无需改动；
  4. 停服窗口内切换，旧库只读保留；
  5. 切换过程中的任何冲突、失败，立即停下告知负责人，不自行绕过（项目规则）。


### 10.1 部署就绪与迁移执行单（建议，新增设计）

1. **盘点与演练**：记录实际 D1 schema/触发器、现有协议和金额序列化、在途请求、审计与渠道密钥加密方式；制作隔离副本，验证 PG 映射、金额精度、时区、索引、角色及密钥解密。不能假定旧密文可直接搬库使用。
2. **恢复准备**：演练 PG 全量 + WAL 与主密钥分别备份/联合恢复，验证对象引用；保存导出摘要、行数、分账户余额、请求状态计数及账本校验结果。备份完成不等于恢复可用。
3. **停写与收口**：进入原定停服窗口，停止新预占与新考试/调试创建，排空或登记每个在途请求；旧 worker 停写后导出最终一致副本。未结请求迁移后由哪个实例唯一接管必须明确。
4. **导入校验**：按外键依赖导入，保留用户、公开模型 ID、流水业务身份和审计；校验余额恒等式、逐账户余额、请求状态计数、配置 revision、密钥可解密和模型权限。一项不一致不切换。
5. **切换与观察**：确认仅一个服务拥有账本写入权，再切反向代理/服务；先使用独立验收账户真实模型检查，逐步放量。旧库保持只读，不允许新旧两边同时扣费。
6. **交接**：记录切换点、数据版本、验证证据、监控值班与回滚责任人；确认对象/令牌/worker 清理。任何冲突或失败立即停止并告知负责人。

### 10.2 灰度、回滚与灾难边界（建议，新增设计）

- API/worker 就绪须验证 PG、配置与密钥加载、必要 Redis 能力和对象存储；存活与就绪分开。PG 不可用停止新扣费请求，不能只在 Redis 排队后向客户端承诺已预占。
- Redis 不可用时限流、粘滞、队列、冷却如何降级待确认；不得无上限放行或丢失考试任务。对象存储失败不发布不可下载版本，沙箱宿主失败不影响无关 API 的资源预算。
- 灰度建议按受控账户/流量批次，先验证只读模型目录和非付费试算，再真实低量请求，最后 Studio/考试。流量比例、观察窗口、告警阈值和批准人待确认，本文不擅设数值。
- 可回滚功能配置（高级路由、`newapi` 同步、市场展示、考试调度）与数据库迁移分开管理；关闭考试调度应停止新任务并安全处理在途任务，不能丢弃已发生费用。
- PG 尚未发生新写入时，可按预案切回旧只读副本并恢复旧服务写权；**PG 已有新账本写入后，不得直接切回旧库**。需先停写、对账及负责人批准的数据回迁/向前修复方案，避免余额与审计分叉。
- 代码回滚需保证当前 schema/配置向后兼容；建议 expand/contract，灰度期不做不可逆删列。恢复旧价格仅影响新请求，不改已冻结快照；恢复旧 Bot 版本不能伪造其新考试成绩。
- 回滚触发条件建议涵盖负余额风险、恒等式失败、重复扣费、凭据泄露/沙箱越权、系统性错误和不可恢复队列积压；具体阈值待确认。安全事件先停止受影响入口并保全脱敏证据，不擅自恢复流量。

### 12.3 里程碑证据与放行（建议，新增设计）

- 单元测试、协议/事务集成测试及故障注入可使用夹具证明确定性边界；它们不能替代原定真实模型里程碑验收。
- 真实模型验收使用隔离 fixture，不操作用户 live app 或数据；按 `docs/verification/README.md` 执行。涉及托管 Bot 模型可用性先核对 `docs/gateway-deployment-193.md`，不能由配置空字段推断不可用。
- 模型驱动浏览器验收按 `docs/bot-model-browser-acceptance.md`，记录实际模型、Bot 名称、自然语言任务、每步动作、耗时和独立观察结果；脚本直接调用工具及假响应不能算真实模型完成任务。
- 每阶段交付证据包括配置/代码版本、隔离环境、输入、请求/考试 ID、脱敏 trace、账本校验和观察结果；失败项及待确认项不标完成，不以“接口返回成功”代替结果验证。
- 放行顺序建议为安全/账本检查 → 协议兼容 → 真实模型端到端 → 迁移恢复演练 → 受控灰度 → 扩量；任何安全或账本门禁失败停止并告知负责人，按第 10 节决定恢复，不自行绕过。
